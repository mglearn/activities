# Google Classroom Add-on: Plan

**Covers:** Gen AI Literacy Breakouts + Digital Citizenship Breakouts (Classroom Editions)
**Status:** Planning, drafted 2026-10-23. Nothing is built yet.
**Today's alternative:** the completion-code Classroom Edition (`assets/classroom.js`,
`classroom.html`, `classroom-check.html`). It stays live for everyone the add-on can't reach.

---

## 1. Goal

A teacher in Google Classroom clicks **Add-ons**, picks a breakout, and assigns it. Students
play it **inside Classroom**. When they open the fourth lock, **the grade lands in the
Classroom gradebook automatically**. There are no codes, no copy/paste, and no checking step.

Out of scope for v1: the 🕹️ Arcade games (ungraded, so they stay as links/Material) and
analytics beyond complete/incomplete.

## 2. Facts that shape the plan (verify before starting; Google changes these)

| Fact | Consequence |
|---|---|
| Teachers need a **Google Workspace for Education Plus** or **Teaching & Learning** license to use add-ons. Fundamentals/Standard districts can't. | The add-on reaches *fewer* teachers than the code edition, so **both editions coexist**. The add-on should show unlicensed teachers a clear "why not + use the code edition" message (Google recommends this). |
| Add-on attachments can only be **created and assigned on Classroom web**. Students may open them on mobile. | Teacher flows are desktop web only. Student flow must work on Chromebooks and iPads (the pages already reflow). |
| **Five iframes:** Attachment Discovery (teacher picks content), Teacher View, Student View, Student Work Review, Link Upgrade. | We build four small pages plus an optional link-upgrade handler (sec. 4). |
| **Activity-type attachment** with `maxPoints` → we must set `pointsEarned`, via `PATCH courses.courseWork.addOnAttachments.studentSubmissions`. The "Grade sync" attachment updates the student's **draft grade**. | This is the core feature. The teacher still clicks Return, which is normal Classroom practice. |
| Google **recommends stored offline teacher credentials** (refresh + access tokens) so grades post the moment a student finishes. The alternative only posts grades when the teacher opens each submission, 5–30 s each. | **We need a backend with a small database** that stores teacher tokens. This is the biggest architectural change: today's suites have no server. |
| **Google SSO is required** (teachers, and students if they sign in). Sign-in must be silent on return visits, using the `login_hint` Classroom passes. | Google Identity Services + OAuth on the backend. No passwords of our own. |
| Scopes `classroom.addons.teacher` / `classroom.addons.student` are **sensitive**. They need **OAuth verification** (demo video, typically 3–5 working days for sensitive-only scopes). | Budget time for the video and privacy-policy pages. |
| **Marketplace review** runs Google's published *add-ons test plan*, using Google-provided test accounts on `marketplacetest.info` (teacher, teacher2, student, student2) added as Draft Testers. Failed tests add significant delay. | Run the test plan ourselves before submitting (sec. 6, Phase 4). |
| Required UX rules: do everything inside the iframe; a **Turn in** button must call the turnIn API; render student work in Student Work Review with no navigation between students; never show an error page when an assignment or course is **copied**; WCAG 2.1 AA is recommended and self-reported. | These become acceptance criteria. The suites already target accessibility. |

Sources: developers.google.com/workspace/classroom/add-ons (overview, requirements v1.1,
grade-passback walkthrough, review process); support.google.com/edu/classroom/answer/12351654.

## 3. Architecture

```
 Google Classroom (web/mobile)
   │  iframes (HTTPS, allowed URI prefix registered in the Marketplace SDK)
   ▼
 addon.<our-domain>  ──────────────────────────────────────────────┐
   ├─ /discovery    teacher: browse suite → grade → activity → Attach │  static pages built by the
   ├─ /teacher      teacher preview of an attached activity           │  existing generator, plus
   ├─ /student      the breakout itself + "Turn in"                   │  one small bridge script
   ├─ /review       per-student status: solved? when? which locks?   │  (assets/addon.js)
   └─ /api/*        OAuth callback, attach, complete, turn-in         ┘
                        │
                        ▼
                small DB: teachers(google_id, refresh_token[encrypted], access_token, expiry)
                          attachments(course_id, item_id, attachment_id, activity_id, teacher_id, max_points)
                          completions(attachment_id, submission_id, student_google_id, solved_at)
```

- **Content stays generated by the current pipeline.** Add one build target
  (`scripts/gen-addon.js`) that writes the four iframe pages and swaps `classroom.js`
  (codes) for **`addon.js`**, which listens for the engine's existing win event (the
  `ctob-complete` `postMessage`, or the same `#win.show` observer `classroom.js` uses) and
  calls `/api/complete`.
- **Backend:** recommend **Google Cloud Run** (a container: Node + Express) with
  **Firestore**, in the same Google Cloud project as the OAuth client. One provider, a free
  tier that likely covers a pilot, and Secret Manager for the token-encryption key.
  *Alternative:* the existing Linode (Node or PHP + SQLite/MariaDB, like the LMS work). This is
  cheaper if it's already paid for, but we'd own patching and TLS.
- **Grade flow:** student wins → `addon.js` POSTs `{attachmentId, submissionId}` (from the
  iframe URL params) with the student's ID token → backend verifies the token, confirms the
  submission belongs to that student, records the completion, loads the **teacher's**
  stored credentials, and `PATCH`es `pointsEarned = maxPoints` → Classroom updates the draft
  grade. The student then clicks **Turn in** (turnIn API).
- **Anti-cheat is still light-touch.** The answers live in the client locale files, just as
  today. A stronger v2 option: `addon.js` sends the four lock answers and the server checks
  them against the English source JSON before granting points.
- **Everything is free.** All 18 breakouts per suite are free and open, so the add-on shows
  every activity to every teacher. There's no content licensing or district gate. (The only
  "license" involved is Google's own requirement in sec. 2.)
- **One add-on or two?** Recommend **one add-on, "Critical Thinking Breakouts,"** with both
  suites (and room for more CTOB suites) in the Discovery picker. That means one Marketplace
  listing, one OAuth verification, and one review.

## 4. The iframe pages

| Iframe | What it shows | Notes |
|---|---|---|
| **Attachment Discovery** | Suite → grade band → activity cards (reuse library data), language picker, "Attach" | Creates the attachment via `addOnAttachments.create` with `teacherViewUri`, `studentViewUri`, `studentWorkReviewUri`, `maxPoints` (default 100, teacher-editable). Must also say how to attach content found elsewhere. |
| **Teacher View** | Read-only playable preview + launch-page summary (premise, CLEAR mapping, TEKS) + link to the answer key | Reuse the launch-page HTML from `gen-site.js`. |
| **Student View** | The breakout + a **Turn in** button after the win | `?lang=` default from the browser language (a Google requirement, and already our i18n order). Never pop out to a new tab. |
| **Student Work Review** | One student: solved ✅/not yet, time solved, attempts per lock (optional) | No navigation between students. |
| **Link Upgrade** *(optional, v1.1)* | Turns a pasted breakout link into an add-on attachment | Google recommends it, and it's nice for teachers who already post links. |

**Copied assignments/courses:** when Classroom copies an assignment, our attachment IDs are new.
The pages must look the activity up from the attachment's own URIs (we encode
`activity_id` in the URI), never fail on an unknown attachment, and lazily create the DB row.

## 5. Privacy and legal (we now handle student data)

The code edition collects nothing. The add-on stores **student Google IDs, completion times,
and teacher OAuth tokens**. Before launch:

- Privacy policy + Terms pages for the add-on (required for OAuth verification and the
  Marketplace). Reuse the PROTECT-reviewed LMS policies as a starting point: retention
  periods, a subprocessor table (Google Cloud), encryption at rest.
- **Data minimization:** no names or emails stored (Google IDs only, with names fetched live
  for the review view), completions deleted N days after the course ends, tokens deleted
  when the teacher revokes access.
- **Texas districts:** be ready to sign the **TX-DPA** (Student Data Privacy Consortium,
  Texas Student Privacy Alliance). FERPA "school official" framing, COPPA via school
  authorization (K–5 students are under 13).
- Decide **who the publisher is** (TCEA vs. personal/mglearn). It goes on the Marketplace
  listing, the OAuth consent screen, and the DPAs.

## 8. Risks

- **License gate.** Many Texas districts run Fundamentals and can't use add-ons. *Mitigation:*
  the code edition stays first-class.
- **Google policy/API churn.** The requirements doc was revised in 2024, and the review process
  has changed sequence between versions. *Mitigation:* join `classroom-dev-announce`; re-verify
  sec. 2 at Phase 0.
- **Token custody.** Refresh tokens expire after 6 months of disuse, password changes, or
  revocation. *Mitigation:* fall back to "grade posts when the teacher opens Student Work
  Review," and show a re-authorize prompt in Teacher View.
- **New data-protection obligations** (sec. 5). This is a real step up from "collects
  nothing" and must be in place before any student data flows.
